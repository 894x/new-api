# 按用户保存请求与响应

采集默认关闭。在管理员 **用户管理 → 编辑用户 → 保存请求与响应** 中按用户开启或关闭，开关独立保存并立即作用于该用户的新请求。已开始的请求使用开始时的配置；关闭不会删除已采集数据。

管理员在 **使用日志 → 详情 → 请求与响应** 中查看状态，点击“查看采集内容”才读取正文，可以复制或下载 JSONL。普通用户和 API Key 日志接口不返回正文，独立读取接口也要求管理员认证。查看正文和修改开关会生成管理审计日志。

## 覆盖范围

- `POST /v1/chat/completions`、`/v1/completions`、`/v1/responses`、`/v1/responses/compact`、`/v1/messages`。
- 用户入口请求、返回用户的响应，以及共享 HTTP 转发边界处每次网关尝试的上游请求和响应。记录渠道、实际模型、HTTP 状态和上游请求 ID。
- JSON 和 SSE；HTTP 解压后的应用正文，不是 TLS/HTTP 线缆抓包。SSE 保留接收顺序，文件中的一条记录对应一段完整或受限正文，并非一次网络分包。
- 自定义 SDK 或绕过共享 HTTP 边界的适配器只采集可观察到的部分，标记 `partial / upstream_not_observed`。不包含 WebSocket、Playground、二进制媒体、异步任务及 HTTP 库内部的透明网络重放。
- 鉴权通过后才决定采集。限流、路由拒绝等发生在正文读取之前时，正文会标记为不完整；不为了取证额外读取被拒绝的请求。

## 存储与部署

主数据库保存独立的 `request_capture_policies` 和 `request_captures` 表；不把正文写进消费日志 `other`，不依赖日志库类型（包括 ClickHouse）。SQLite、MySQL、PostgreSQL 使用同一组 GORM 模型。

压缩正文存放在：

```text
data/request-captures/YYYY/MM/DD/HH/<capture-id>.jsonl.gz
```

目录日期按 UTC。`.store-id` 是该持久化卷的标识，必须和正文一起保留；记录中的请求 ID 与消费日志关联，文件名使用独立随机 ID。JSONL 首行为格式和请求元信息，后续每行是一段正文记录。

在 **系统设置 → 运维 → 日志维护 → 请求采集存储** 中修改保留天数与每实例容量上限，点击“保存采集设置”。两项作为一个配置原子保存，必须是 1–365 的整数。默认仍为 3 天、10 GiB；更改不会自动开启任何用户的采集。

- 保存后本实例无需重启。保留天数作用于新采集的记录，已有记录的到期时间保持不变；延长保留期不会恢复已删除文件。
- 容量上限立即用于新的归档；后台每分钟检查容量变更，调小后淘汰最旧的归档。正常情况下约一分钟内开始清理，繁忙或磁盘异常时可能延后。
- 多实例通过现有系统配置同步周期加载新值，每个实例独立应用相同容量上限。
- 配置持久化到主数据库 `options` 表的 `RequestCaptureStorage`，不再读取 `REQUEST_CAPTURE_RETENTION_DAYS`、`REQUEST_CAPTURE_MAX_GB` 环境变量。

目录仍通过环境变量配置，修改目录需重启：

| 环境变量 | 默认值 | 说明 |
| --- | --- | --- |
| `REQUEST_CAPTURE_DIR` | `data/request-captures` | 正文持久化目录，相对路径基于进程工作目录 |

存储初始化失败时转发继续正常工作，管理员界面显示存储不可用。

容器必须将 `REQUEST_CAPTURE_DIR` 挂载到持久化卷，例如设置 `/data/request-captures` 并挂载 `/data`。不要把目录放到静态站点目录中。目录权限请求为 0700、文件为 0600；Windows 上还需要依靠目录 ACL 控制访问。

**当前实现是单进程拥有一个本地卷。** 多实例应各用独立卷；管理员需要通过产生记录的实例读取该实例的正文，访问其他实例显示“采集存储不可用”。本版未接入 S3，也未实现跨实例取证文件路由；不要让多个进程同时写同一目录。数据库策略可以共享，开关会被每个实例的新请求直接读取。

## 容量与完整性

- 每次请求正文头部共享 4 MiB 内存预算；每段响应额外保留最后 64 KiB，以便长 SSE 截断后仍能看到末尾 usage。最多记录 8 次网关上游尝试。
- 最多同时保有 8 个采集会话（包括等待持久化的会话）；超出会写入 `failed / capacity_exceeded` 索引，不阻塞转发。
- 文件压缩、写入和容量淘汰在有界后台队列中进行。最终文件用临时文件加重命名发布。临时文件、数据库索引与备份不计入已归档正文容量上限，应另外预留磁盘空间。
- 每小时清理过期文件；达到容量上限时提前淘汰最旧的已归档文件。正文过期后保留小型状态索引至原到期时间后 7 天，消费日志不受影响。
- 正常关闭在 HTTP 请求排空后等待队列落盘，最多 10 秒。异常退出可能丢失仍在内存中的正文；重启会将 `recording` 标记为 `failed / process_interrupted` 并清除未完成和孤立文件。
- `complete` 仅表示观察到读完/写完，不代表模型业务成功；`truncated`、`omitted`、`redacted` 分别表示截断、省略、脱敏。`tail` 是单独尾部片段，不能与 `body` 拼接假装是完整响应。
- 采集失败不影响正常请求、流式 Flush 或计费。

## 脱敏与分析

不采集认证请求头、Cookie 或 URL 查询参数。JSON 中常见密钥字段递归遮蔽，独立 URL 字段移除 userinfo、query 和 fragment。普通 prompt/messages 内容保留用于分析，因此正文仍属于敏感数据；脱敏并不保证识别自然语言中人为粘贴的所有秘密。

可解析且无需脱敏的 JSON/SSE 数据内容保持原样；需要脱敏的 JSON 会重新序列化并标记 `redacted`。无法安全解析的截断 JSON、非 JSON 内容和不支持的 SSE 行会省略并标记 `omitted`。完整超长请求如需保留，应先评估并调整代码中的内存预算，不能把省略内容当成空请求。

缓存分析时对照：用户原始输入 → 实际上游输入 → 上游原始 usage → 同一请求 ID 的消费日志缓存 token 和计费口径。不同供应商统计口径不同，采集功能本身不修改计费或缓存命中率公式。
