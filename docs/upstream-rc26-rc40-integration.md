# Incremental upstream integration: rc26 to rc40

## Scope and preservation rules

- Start: fork commit `317081814da2c7c8096758ecdc0f76b330745e28`, based on upstream rc25.
- Integrate each upstream RC in order and verify it before advancing to the next RC. The owner additionally approved splitting the rc27 migration into shared-foundation commits and one verified migration commit per channel; do not batch all channel migrations into one large commit.
- Preserve fork functionality; ask the owner before resolving duplicated features.
- Work on `codex/rc26-to-rc40` in an isolated worktree. Original checkout changes remain untouched; reconcile its pending request-body/copy optimization separately before final handoff, with ownership and regression checks.
- Do not push, deploy, or migrate production databases as part of local integration.

## Confirmed feature decisions

- rc26: retain the existing group/model RPM/TPM configuration and inheritance semantics; merge upstream expanded request counts and overflow protection.
- rc27: converge on the JS task plugin architecture and migrate all existing custom task functionality, including Doubao, MiniMax, Wan, Seedance SLS, Tencent TokenHub, and asset-library integration. Do not retain two permanent task execution pipelines.
- rc27 billing decision: the owner explicitly chose upstream Seedance 2.5 1080p multipliers: 11.7/10.7 without video input and 7/10.7 with video input, replacing the fork's 77/70 and 46/70. This is an intentional billing change, not a lossless migration. Other configured pricing remains unchanged.
- The owner resolved the outstanding rc27 choices: retain Ollama's existing Claude conversion and add a native-mode switch; remove the PR auto-check/close workflow following upstream. The latest Hailuo decision supersedes the earlier preservation choice: adopt upstream non-H3 parameter defaults, precedence, normalization, and model-combination validation, without a legacy behavior mode. H3 custom capabilities, billing safety, and access to persisted task results remain in scope. Earlier pending-choice entries below are historical; implementation and verification are recorded separately.

## Channel migration commit boundaries

- Commit shared plugin infrastructure separately from channel-specific migrations. Preserve the current merge resolutions and untracked migration tests while organizing the existing in-progress merge; do not abort or discard the work to obtain a clean index.
- Commit each channel's plugin implementation and independently executable contracts separately. The shared host changes the adaptor response interface and routing together, so source commits retain the old Go routing; shared host activation, host-dependent regressions, and legacy-driver removal follow after the provider implementations are ready. Do not introduce a second temporary compatibility architecture just to make the commit split possible. Include the approved Seedance 2.5 multiplier change with the Doubao implementation.
- Before labeling a channel migration complete, verify its existing custom features, request and query contracts, historical task compatibility, authorization and asset ownership, and applicable charging/refund behavior. Source deletion alone is not evidence of a completed migration.
- Keep unfinished channel work out of completed migration commits. Retain required legacy functionality during the transition; the final rc27 result must use the unified plugin architecture, not two permanent execution pipelines.
- Run the full integration checks and record the final rc27 integration commit before moving on to rc28. Per-channel commits do not mean rc27 as a whole is ready to deploy.
